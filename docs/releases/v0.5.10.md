# ATape v0.5.10: Source clocks and recorded activity

This coordinated release contains the CLI and all seven official Adapters at
0.5.10, with matching Web, Server and container metadata. The Authentication
epoch remains `auth-v1`, including the 180 days absolute Web Session lifetime.
Unified release and minimum CLI metadata are 0.5.10. Package publication,
Server rollout and Web deployment are separate operations.

## Codex source clocks and record order

The Codex paged Adapter now explicitly selects nullable Canonical v3. Supported
records with missing, null or invalid source timestamps remain captured with an
unknown occurrence time. Session recency uses the maximum admitted source clock
in the selected metadata/title/record snapshot, or remains unknown. Filesystem
modification time supports discovery, revision and stable legacy observation/Raw
capture metadata; it does not fill a missing Session or Event clock. Repeating
an unacknowledged Raw chunk reconstructs the same receipt metadata.

Each supported projected source record has a stable order coordinate. A persisted,
bounded source-object/generation registry gives file generations separate
namespaces, preserving existing coordinates through append, discovery reorder
and source deletion. Missing or reversed clocks do not reorder records or fold
distinct user inputs together. Ordering separate files in one Thread is derived.

Projection v5 replays supported older Canonical cursors once with stable Event
IDs and a higher revision floor, retaining Raw acknowledgements. Available
source history can therefore acquire corrected clocks. Unavailable history
remains unrepaired; the Server does not guess away a stored epoch. The updated
cursor cannot be read by an older Codex Adapter. This remains the legacy paged
collection path, with its existing source-dependent retry and redaction-policy
limits; it does not gain sourceCapture frozen recovery or complete publication.

The new Host must affirm the Adapter's explicit v3 capability. Collection and
managed admission require affirmative Server support before source access or
progress changes. The CLI-authenticated Canonical capabilities endpoint reports
modern profiles independently of Publication; an explicitly absent endpoint
can use the existing affirmative publication-target-v3 capability on an older
Server. Negative, invalid, authentication or transient responses are not proof
of support.

See [Codex source clocks](../adapters/codex.md#source-clock-quality-and-replay),
[Canonical ingestion](../api/canonical-ingestion.md), and
[ADR-0122](../architecture/adr/0122-explicit-legacy-source-clocks.md).

## Recorded activity and original records

Session Analytics v3 adds record span, an activity timeline and interval
evidence. Select all captured Threads or one Thread. Summary, tools,
capabilities and usage still describe the full Session. Counts describe
Canonical records, including fragments and tool updates, rather than inferred
turns. Span is the difference between the first and last eligible recorded
clock; it is unknown with none and zero for one instant. It does not establish
work time, active coding time, tool duration or time to first token.

Non-null clocks under explicit nullable Canonical v3/v4 are categorized as
recorded, rather than independently verified. Explicit null clocks are unknown.
Older non-null clocks retain their stored dates and a legacy category, outside
the dated timeline and span. This conservative rule can exclude legitimate
legacy dates; source replay under a nullable profile is required for inclusion.
Unknown and legacy records remain available in a separate unplaced selection.
Existing summary known/unknown counts keep their earlier non-null/null meaning.

The Server produces at most 60 uniform dated intervals, including empty ones.
Select an interval or the unplaced group to page through its records, then open
an Event in the existing conditional Reader. Browser Back restores the selected
Thread, interval and page. Ranges and cursors bind the Session, snapshot,
analytics version and filters. Changed content requires a full refresh, which
clears those selections. Authorization is checked on each read.

New Web opts into v3 using the standard safelisted `Accept` header. New Server
keeps analytics v2 for callers without that opt-in. Older Servers can return
v1/v2; Web keeps their supported report and explicitly marks activity
unavailable. Missing activity is not a zero report. The Module reads authorized
Canonical metadata without Raw or Search data, new persistence or background
workers. Existing deadline and capacity bounds remain enforced. Arbitrary
client time bounds, timeline granularity, cost estimates and generated analysis
remain outside this release.

See [Session Analytics](../session-analytics.md) and
[ADR-0123](../architecture/adr/0123-recorded-activity-ranges.md).

## Upgrade and recovery boundaries

The actual SQLite journal, `atape.client.v3-capture.v2` state contract,
update-control v1 and compiled `journal-v7-to-v8` plan remain unchanged. A common
state contract does not prove that an older parent understands a new Adapter
manifest or can resume a newer Codex cursor.

The genuine published 0.5.9 parent rejects a first managed update involving
active Codex collection during read-only preflight, before pause. Stop sync
before updating the CLI and matching official Adapter bundle. Preserve
`ATAPE_HOME`, credentials, project/tool choices, checkpoints, Raw receipts and
Stop intent. The required POSIX installed transition gate executes the genuine
old console's stopped complete-bundle update, followed by the exact candidate
Collector's replay, no-op and append cycles. It verifies preserved checkpoint
and credential bytes, Raw receipts, stable Event IDs and higher revisions,
including an Instance advertising minimum CLI 0.5.10 during upgrade. Its Server
and distribution HTTP are owned external Test Adapters; constructed source
records do not establish live Provider acceptance or a personal installation
upgrade. Do not install the new Codex Adapter into the old Host, or resume with
an older Adapter after the new cursor is written. Consult
[the stopped Codex upgrade](../cli/setup-and-adapters.md#codex-source-clocks-059-to-0510)
and [the Codex guide](../adapters/codex.md#source-clock-quality-and-replay).

Other historical boundaries still apply. In particular, active official-Claude
0.5.8 installations require the stopped external CLI refresh described in
[v0.5.9](v0.5.9.md#upgrade-and-recovery-boundaries). Pinned, local, custom or
nonselected integrations are not silently replaced. Normalized MCP/Skill
identity remains Claude-specific; no identity is inferred for other Providers
from text or display labels.

No database migration is added. Preserve the current Server image and a fresh
paired PostgreSQL/Raw recovery point before rollout. Restoring that point
withdraws writes made afterwards; a backup is not evidence that production
restore or rollback was exercised.

## Candidate validation and manual acceptance disclosure

The exact frozen candidate must pass fresh repository, installed CLI/Adapter,
historical compatibility, PostgreSQL, dependency/container security, race/fuzz,
self-host configuration and paired restore gates. Feature PR results and
0.5.9 evidence do not attest this release candidate. Published npm bytes,
GitHub assets, update catalogs and deployed image identities require their own
verification; this release note alone does not claim that those actions passed.
