# ATape v0.5.4: Login startup and Claude conversation continuity

The CLI and all six official Adapters use version 0.5.4. This release adds
login startup with a durable Start/Stop preference, and includes the Claude
current-path, legacy-adoption and direct background-child changes integrated
since 0.5.3.

## Install and update

Use Node.js 24 or newer and a macOS or Linux terminal:

```sh
npm install --global @atape/cli@0.5.4
```

**0.5.4 requires one manual upgrade from 0.5.3 or older.** It declares
`atape.client.v3-capture.v2`: the 0.5.3 automatic updater rejects this different
state contract before activation and keeps its current installation. Unified
package versions do not make the new Claude state readable by an old runtime.

Before installing, use the old CLI to Stop sync and finish any interrupted
update recovery, close old consoles, and keep a consistent backup of local
state. Run the npm command above outside the old console, then open the new
console. The new CLI preserves the selected official Adapter records and user
preferences while retiring known v1 runtime pointers. Busy, unknown or
unfinished old state blocks migration with recovery guidance. Help and version
queries do not migrate state. Use Tools to update installed official Adapters
to 0.5.4, inspect the Server prerequisite below, then explicitly Start sync.

Do not complete this transition through an already-open 0.5.3 console. If old
pending work prevents entry, restore the old npm CLI, finish that work and Stop
sync, then retry. After SourceCapture v2 has migrated a journal or adopted a
legacy Session on the Server, recover through a v2 runtime; do not downgrade to
0.5.3. A local backup cannot undo Server adoption.

Later compatible v2 releases use the existing automatic schedule and compatible
rollback. Successful checks run every 24–30 hours. Updates prepare one exact
CLI/official-Adapter version and preserve custom, local, archive and URL sources.

## Login startup

Initialization enables login startup by default. Configurations without an
explicit startup preference also default to on. **Settings → Turn off login
startup** disables future starts without stopping current collection. Settings
shows the saved preference separately from actual native registration and
offers a registration retry when needed.

Supported npm-global installations register a user LaunchAgent on macOS or a
systemd user service on Linux. Linux requires an available user manager; ATape
does not enable linger or install a root service. Windows, source development
builds and other package managers are unsupported. This is login recovery;
it does not continuously supervise a crashed Collector.

The headless coordinator recovers interrupted automatic updates and resumes
only configured sync the user still wants running. Start saves that intent and
its schedule. Stop clears it durably, even if its process has already gone away;
login and upgrades cannot revive it. Update pauses preserve intent. Existing
stopped legacy installations must use Start once to establish wanted sync.

An owned stable coordinator uses the manually installed 0.5.4 npm bootstrap;
a 0.5.3 bootstrap cannot read a v2 managed pointer. Later compatible managed
releases can reuse that capable bootstrap. The CLI declares
`atape.login-startup.v1` alongside `atape.runtime.v1` and
`atape.client.v3-capture.v2`. After an update,
reopen an older console before Start or settings changes: its old Start cannot
override a newer durable Stop. Preserve process/intent metadata with capture
state; manually deleting it can conservatively stop future recovery.

Registration preserves required provider paths, explicit HTTP/source-admission
settings and limited private proxy/CA/redaction context. It does not copy the
whole shell environment, account credentials or conversation bodies. No remote
log recall or diagnostic-log upload is included. See
[login startup and recovery](../cli/setup-and-adapters.md#login-startup).

## Claude current paths and background children

The Claude Adapter publishes the source-indicated current conversation through
sourceCapture v2, including explicit rewind, empty paths, validated compaction
continuity and explicit adoption of existing legacy Sessions. Proven direct
background children can append while the parent file is unchanged; native typed
completion notifications stay Raw-only. Nested children, child forks and
cross-file adoption remain outside the supported scope.

Claude requires a compatible Host and a Server advertising publication v2
targets and legacy adoption. The Collector checks these capabilities before
opening or migrating its account journal and legacy checkpoint; an unsupported
Server leaves that source's local state unchanged. Package publication does not
add those capabilities to an existing Server. Operators must satisfy this
prerequisite before enabling the new Claude path. Preserve complete local capture state. See
[Claude support and limits](../adapters/claude.md).

## Validation and manual acceptance disclosure

Automated publication gates must pass for this candidate: repository checks,
production builds, exact installed tarballs and updater/login/terminal behavior,
authenticated HTTP/PostgreSQL and historical Adapter contracts, dependency and
container security, Go race/fuzz, supported self-host configurations and paired
restore. The auth-v1 protocol and 180 days absolute Web Session lifetime are
unchanged.

Native-manager acceptance is limited to isolated registration, a successful
empty bundled helper and owned cleanup on macOS, plus Linux unit parsing.
Real logout/login, machine reboot, power loss, native-launched conversation
delivery and Linux Collector/user-manager cgroup lifecycle remain unverified.
Historical journal acceptance uses the unmodified 0.5.3 implementation to create
v7 Canonical/Raw obligations, then verifies forward migration and restart
recovery through the current journal Interface; that old reader rejects v8.
Controlled updater tests cover compatible v2 updates. Any post-publication
public-package acceptance, including actual 0.5.3 rejection of this release, is
recorded separately with the exact downloaded bytes. No cross-contract automatic
upgrade or 0.5.3 rollback is supported. See
[ADR-0104](../architecture/adr/0104-capture-v2-state-upgrade.md).
