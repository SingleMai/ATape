# ATape v0.5.7: Explicit capture migration and unattended update recovery

This release adds an explicit, recoverable local capture migration to the managed
update path. The coordinated npm bundle contains `@atape/cli` and the seven
official Adapters, all at 0.5.7. Publication and unattended delivery are separate
results: this candidate must pass its automated gates before publication, and
public packages alone do not establish a successful production-registry upgrade.

The Authentication epoch remains `auth-v1`, including the 180 days absolute Web
Session lifetime. Artifact release and minimum CLI metadata are 0.5.7. Publishing
npm packages does not deploy a Server or change an existing Instance's minimum
CLI version.

To refresh the actual command entry with Node.js 24 or newer:

```sh
npm install --global @atape/cli@0.5.7
```

## Explicit local migration and continued compatibility

The first compiled plan is `atape.capture-migration.v1 / journal-v7-to-v8`. A
migration-capable capture-v1 or capture-v2 runtime can move registered journals
at format 7 or 8 to actual capture contract `atape.client.v3-capture.v2`.
Transactional v7-to-v8 SQL preserves bindings, Canonical and Raw obligations,
receipts and checkpoints; verified v8 is an idempotent no-op. Projects, tool
selection, credentials, privacy settings and Stop intent are retained. Manual
upgrades use the same migration path for retained journals even when tools have
been disconnected. This does not import history or migrate Server storage.

The verified target performs read-only preflight before the bounded collection
pause. For enabled SourceCapture v2 sources that are intended to run, it checks
the Server's publication and legacy-adoption capabilities using existing
credentials. An Adapter's declared publication profile determines its minimum;
Cursor requires Profile3. Stopped collection permits local migration without
remote prerequisites. Scope and inventory are checked again under ownership so
a concurrent Start or configuration change cannot reuse an obsolete preflight.

Before the durable forward boundary, a confirmed failure can restore the exact
previous selection. After that boundary, recovery must continue with the recorded
target and plan. A strict requirement, progress ledger and completion receipt
gate ordinary capture writes. Recovery checks each attempt's authority under the
same barrier as the reader floor; a revoked apply process cannot commit further
progress. Missing metadata can be repaired only from matching surviving evidence;
unknown or inconsistent state fails closed. Do not delete recovery metadata as
a repair.

A completed receipt permits later compatible runtimes at or above its target,
subject to the current reader floor. It does not pin an obsolete executable,
bootstrap identity or Adapter slot. An active controlled-session creation proof
defers a floor advance until confirmation or abandonment, without killing the
interactive native session or allowing stale writers past the floor.

Migration-capable clients prefer the fixed v2 catalog, whose routes bind source
contract, control protocol and known migration plan to a complete immutable
bundle. The original v1 catalog and descriptor remain compatible; their readers
require the original seven packages and accept bounded additive packages. The
current publisher verifies all eight packages, including Cursor. New Adapters
are not installed or enabled merely because a bundle contains them. Old plan
routes and a real capture-v2 bridge on legacy GitHub/npm latest must remain
available for indefinitely offline clients. Future state formats and plans need
their own implementation, recovery bridge and verification; this release does
not authorize arbitrary migrations from remote metadata.

See [explicit migration behavior](../cli/setup-and-adapters.md#explicit-capture-migration)
and [ADR-0115](../architecture/adr/0115-explicit-capture-migrations.md).

## Independent wakeup and older installations

Automatic updates are enabled by default after tool initialization and can be
disabled in Settings. Supported npm-global macOS/Linux installations register an
independent hourly user-level wakeup. It checks the existing due schedule while
the console is closed, login startup is off or collection is stopped, without
issuing Start. Disabling updates stops future new work; scheduling needed by an
in-flight update remains available for recovery and is removed when safe.
Recovery after the forward boundary still runs with automatic updates off and
preserves the latest Stop intent.

Immutable 0.5.3 does not acquire migration, discovery or wakeup support from this
release. Its incompatible initial boundary needs the
[documented manual transition](../cli/setup-and-adapters.md#explicit-maintenance-and-external-replacement).
Existing capture-v2 clients can receive a compatible bridge, but a 0.5.4
installation enrolls independent scheduling only after a capable actual entry
runs. A newer managed selection does not prove the npm command entry was
refreshed; new command grammar may require that refresh. Reopen old consoles
after upgrading. External npm replacement is not crash-atomic.

The wake requires a running user manager and an available Node/npm installation.
It does not update a powered-off machine or supervise collection. Controlled
process, SQLite, orphan-process and physical-disk tests exercise recovery
boundaries; native helper tests exercise repeated OS activation. They do not
establish real capture after logout/reboot, calendar sleep, recovery from an
actual machine power cut, or a migration delivered through the production
registry. Those remain unverified operational acceptance limits.

## Cursor and Server prerequisites

Cursor remains experimental. Existing acceptance uses constructed Confab-derived
rows and a synthetic native executable, not authenticated Cursor CLI or IDE
conversations. The selected static profile is Cursor CLI `2026.10.01-e373342`;
other versions, real streaming/compaction and platform equivalence remain
unverified. Controlled creation requires a fresh session through
`atape start --tool cursor`, an updated actual bootstrap, a connected Project,
an enabled Cursor Adapter, an interactive macOS/Linux terminal and an explicit
absolute `ATAPE_CURSOR_EXECUTABLE` path. Unconfirmed history is skipped. A
nonprefix rewrite or truncation conservatively stops that source while keeping
its published head. See the [Cursor guide](../adapters/cursor.md).

**Cursor upload still requires a Server supporting
`atape.publication-target.v3`, storage migration
`000024_unknown_conversation_time.sql`, and matching Reader/Search/Web behavior.**
An older Server fails capability negotiation; source clocks are not fabricated.
Other providers retain their existing publication profile unless they explicitly
declare Profile3. Server deployment and the production storage migration are
separate operator actions and are not authorized or performed by this release.

## Candidate validation and manual acceptance disclosure

The exact frozen 0.5.7 candidate must pass repository checks, production builds,
checksummed installed CLI/Adapter acceptance, terminal and historical-client
contracts, real local migration/recovery contracts, authenticated PostgreSQL
provider contracts, dependency/container security, Go race/fuzz, self-host
configuration and paired restore gates. Prior PR results and older package
hashes are not this candidate's completed acceptance. No candidate CI or
publication outcome is claimed by preparing these notes.

All eight packages use the ordinary GitHub Actions Trusted Publisher route.
Cursor's one-version local bootstrap in 0.5.6 remains a historical record;
neither its skipped 0.5.6 workflow step nor its trust configuration proves a
successful Cursor OIDC publication. The workflow must verify all eight exact
public manifests and tarball bytes before advertising the version Release,
compatible v1 catalog and migration v2 catalog. Publication evidence must cover
the actual frozen 0.5.7 candidate.
