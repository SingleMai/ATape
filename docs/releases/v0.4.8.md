# ATape v0.4.8: Team Overview and structured Token usage

The CLI and official Codex and Claude Adapters now collect structured Token usage
for the Team management dashboard. Input, output, cache read and cache write are
reported separately. Input includes cache Tokens; output includes reasoning where
the source reports it. Unknown values remain unknown rather than becoming zero.
Usage collection works with Raw capture disabled.

Usage records are deduplicated and revised transactionally. Existing Adapter
cursors rescan retained readable history once to backfill supported usage without
duplicating conversations or Token totals. Deleted source files cannot be recovered.

The Team homepage shows shared activity metrics, previous-period comparisons,
Agent trends, member/Project/model details and recent conversation previews. Compact
filters and theme colors keep the view readable. Large snapshot requests still
have an explicit 100,000-fact limit, including the comparison period; the API
rejects incomplete totals rather than silently truncating them. Conversation
reading also renders unavailable captured local-file links as readable text.

## Upgrade

```sh
atape upgrade
atape adapters upgrade --all
```

Or install `npm install --global @atape/cli@0.4.8` with Node.js 24 or newer.
The CLI and both official Adapters use 0.4.8. Preserve ATAPE_HOME and restart
running collectors after a manual npm CLI replacement. Upgrading only the Server
does not add Token collection to previously installed clients.

The receiving Server must include the Team Overview/structured usage implementation
and migration `000014_canonical_usage.sql` before new usage uploads. The existing
atape.net deployment already includes these changes. Self-hosted installations
must upgrade their Server separately. Package publication does not deploy a Server
or migrate a database.

## Source coverage and limits

- Claude uses `message.id` and source position to avoid counting repeated blocks.
  Missing source fields stay unknown; general compaction and unsupported subagent
  recovery are outside this increment.
- Codex counts owned, top-level `token_usage_record.payload.usage`, keyed by Thread
  and response ID. Legacy `token_count` and cumulative snapshots, compaction
  replays, and sources without trustworthy response records remain unsupported.
  The configured turn model does not establish a provider fallback model.
- Historical backfill is best effort. Publishing and upgrading cannot manufacture
  usage absent from the original source. The dashboard discloses reported coverage.
- Cost estimates, budgets, alerts and configurable Team timezone are outside this
  release. The current Team timezone is Asia/Singapore.

See [Team Overview](../team-overview.md) for the shipped scope and next increment.

## Validation and manual acceptance disclosure

Automated repository checks, exact package installation tests, PostgreSQL
integration, dependency/container security scans, race/fuzz tests and self-host
restore gates remain required. The native Claude Adapter/CLI/Go integration
fixture reports 2,010 total Tokens, including 768 cache-read Tokens; replay does
not inflate usage. A real PostgreSQL regression verifies complete metrics and
latest previews with 60,002 messages and rejects reads beyond the supported bound.

The [staging attestation](evidence/v0.4.8-staging.json) remains pending for this
exact release candidate. The unverified manual checks are: GitHub Provider staging
smoke, official-domain egress isolation, official topology, WAF/TLS/callback
configuration, operational backup/restore, observability secret sampling, rollback,
candidate artifact acceptance, two-user/two-Team acceptance, and release signoff.
Earlier dogfood deployment checks are not a complete staging attestation for this
new release candidate.

Manual acceptance is waived, not passed, under the user's explicit request
“发布！” and [ADR-0048](../architecture/adr/0048-release-request-manual-acceptance.md).
Candidate-bound evidence records this authorization. Automated gates are not waived.
The auth-v1 protocol and the 180 days absolute Web Session lifetime are unchanged.
