# ATape v0.2.0 authentication cutover

v0.2.0 is the first authenticated ATape release and starts the `auth-v1`
epoch. The Server, Web application, CLI, Codex Adapter, and Compose build
contract must all report v0.2.0. The minimum supported CLI is v0.2.0.

## Breaking changes

- Anonymous Server and Collector access is removed. There is no compatibility
  flag, mixed v0.1/v0.2 serving mode, or trusted client-supplied User/Team ID.
- Web users sign in through the Instance's configured Provider. v0.2 ships one
  GitHub Provider Adapter; the Authentication Module does not expose GitHub
  claims or tokens to the rest of the product.
- CLI login uses a browser Device Authorization flow and writes one
  Instance-scoped credential below `~/.atape`. The displayed user code is six
  case-insensitive letters/digits and is rendered uppercase.
- Existing CLI configuration requires the explicit `migrate-local-v0.1`
  workflow, then a new login and verified Project setup. Old user/team fields
  never become authority and old checkpoints are not silently adopted.
- Existing self-hosted v0.1.1 data requires the reviewed mapped cutover in
  [the runbook](../operations/auth-cutover.md). Legacy captures stay
  `legacy_anonymous`; v0.2 does not invent a User attribution, and new capture
  lineage can begin at the cutover boundary.

## Deliberately accepted v0.2 risks

- Web Sessions have a 30-day idle timeout and an absolute lifetime of 180 days.
  Rotation, current-session visibility, a 15-minute fresh-authentication guard,
  immediate revocation, CSRF, and exact Origin checks limit exposure.
- CLI bearer credentials do not expire automatically. Their capability is
  limited to visible metadata, Project creation, and upload; they cannot read
  conversation bodies or administer a Team. Users revoke them from Web.
- GitHub is the only v0.2 login entry. Losing the sole linked identity requires
  operator repair; email or username never triggers automatic account linking.
- Authorization uses the application Modules and authoritative PostgreSQL
  lookups, not PostgreSQL RLS. A closed policy catalog, route registry, and
  executable cross-tenant matrix are the compensating controls.
- Provider outage prevents new login and reauthentication but does not disable
  existing Sessions or CLI credentials. Revocation and access reduction remain
  local operations.
- TLS, general traffic shaping, IP reputation, and volumetric protection remain
  the deployment Gateway/WAF's responsibility. The application still bounds
  bodies, polling, code attempts, transactions, and cleanup.
- A lost CLI claim response can leave an active credential whose one-time
  secret was never received. It reveals no secret and can be revoked in Web.

## Rollback and data-loss boundary

Before v0.2 normal traffic, rollback means restoring the same pre-cutover
PostgreSQL and Raw snapshot and its matching v0.1.1 binary. Never roll back only
one side. After any authenticated v1 write, an anonymous binary must not touch
the migrated database. Recovery is forward-only unless an operator deliberately
restores the paired snapshot and accepts loss of every post-cutover write.

The tag remains blocked until the machine-readable gate index and the completed
[staging attestation](evidence/v0.2.0-staging.json) pass release verification.
